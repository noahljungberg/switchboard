# Known issues

Non-blocking problems and follow-ups. Each has the file it lives in and what would fix it. Remove an
entry when it's fixed.

| # | Issue | Where | Fix when it matters |
|---|---|---|---|
| K1 | `wait_for_message` wakes only on mail or revocations written by this process. Admin CLI writes (none deliver mail today) wouldn't wake it, and a `revoke-token` from the CLI doesn't end a held wait early: the wait can't take any mail after the revoke (the token is checked again at read), but it holds until new mail or its timeout (≤ 600 s) and then gets `forbidden`. | `src/core.ts` `waitFor` | Poll the DB every few seconds inside the wait if a second writer appears. |
| K2 | A human's free-text answer in Slack to an `ask_human` is a plain message, not a `human_answer` event, so it isn't marked as "the answer". | `src/slack.ts` `onMessage` | Treat the first reply by the asked human in that thread as the answer. |
| K3 | Windows and the nightly slot are advisory (P1): an agent that ignores `window_status` can still change prod, in or out of the slot. | the systems that make prod changes | M5: those systems refuse a deploy or reconfigure without an approved window id or a covering slot and change id. |
| K4 | A standing rule that depends on live state ("waits until traffic is drained") is only a `note` humans read. | `src/windows.ts` policy | M4: add a policy check against a real status source (`src/status.ts`) once a deployment plugs one in. |
| K5 | The Codex failover is confined less tightly than Claude: its read-only sandbox can still read any file the service user can. That includes the env file and `switchboard.db`, which holds every principal's DMs with the ops agent and their private threads, so a prompt-injected Codex turn could read them (not yet checked against a live `codex app-server`). Claude's `--restricted` confines reads to the context dir. | `src/engines.ts` `CodexEngine` | Run engine subprocesses as a separate unix user that can read only the context dir (systemd `User=` on a helper, or `sudo -u`). Until then, leave `codex` out of `ops.engines` in prod (runbook §5). |
| K6 | Codex `config` keys (`features.shell_tool`, `web_search`) and `thread/start` params were checked against docs and a stub, not a live `codex app-server`. Unknown keys are ignored, so the read-only sandbox and declined approvals are the real guarantee. | `src/engines.ts` | Run `scripts/smoke-engine.ts` with the Codex engine on the host once logged in; adjust keys. |
| K7 | `--restricted` needs claude ≥ 2.1.299 (the subscription engine) and a matching bundled binary in the Agent SDK (0.3.299, pinned in the lockfile). An older one fails every turn, which steps down the chain (announced). | `src/engines.ts` | Pin the CLI version on the host (runbook §0); upgrade the SDK deliberately. |
| K8 | A fresh engine session sees only the last 60 events of a thread. | `src/ops.ts` `render` | The agent can `read_thread` for more; raise `historyEvents` if needed. |
| K9 | Ops turns are at-least-once: inbox rows are marked read after a successful turn, so a turn that answers and then fails (timeout, crash) is retried and may answer twice. | `src/ops.ts` `turnFor` | Skip the retry when the failed turn's grant shows it already responded. |
| K10 | Anything in a shared thread can try to steer the ops agent into `memory_propose`. Every edit is announced in #ops with a revert command, but nothing blocks it. | `src/ops-mcp.ts` | If it happens, require a human's thumbs-up (a button) before memory commits land. |
| K11 | `node src/cli.ts admin usage` sums by calendar month; API credits and spend limits may run on a different billing date. Close to the limit, trust the Console's Cost page. | `src/cli.ts` | Add a `billing_day` config knob if it matters. |
| K12 | One API key pays for turns serving every principal, so whoever owns the key pays for everyone's use. | config / P7 | Allow more than one `claude-api` key (each engine appears at most once in `ops.engines` today), if the humans want costs split. |
| K13 | Unconfirmed: a symlink committed to a context repo (say `repos/x/notes -> /var/lib/switchboard/switchboard.db`) may let `Read` escape `--restricted`, if Claude Code checks the path it was given rather than the target. | `src/context.ts` `ContextRepos`; `--restricted` in `src/engines.ts` | Clone and fetch with `-c core.symlinks=false` (links become plain files), or test `--restricted` against a symlink and record the result. Engines as their own unix user (K5) closes it either way. |
| K14 | Unconfirmed: two `claude -p` turns on different threads (`max_concurrent_turns: 2`) run at once with the same HOME, so they share Claude Code's config and session files and may clobber each other's writes. Same for the SDK engine's `home`. | `src/engines.ts` `ClaudeEngine`, `ClaudeSdkEngine` | A HOME per thread, or confirm Claude Code tolerates concurrent processes on one HOME. |
| K15 | Unconfirmed: Codex is never credential-checked at startup: `buildEngines` skips only Claude engines without credentials, so a logged-out Codex is found out at its first turn or probe (its probe is now a one-word turn, checked against the stub only). | `src/main.ts` `buildEngines` | Check `codex login status` at startup. |
| K16 | Unconfirmed: a window thread's prompt header (the JSON block the engine treats as the system's own) includes the window row, whose `plan`, `rollback` and `verify` the requesting agent wrote, without the `trust: data, not instructions` tag that event lines carry. | `src/ops.ts` `render` | Leave agent-written fields out of the header (the tagged `window_requested` event already has them), or tag them there. |
| K17 | Unconfirmed: a crash in the middle of a git command leaves `.git/index.lock`, and every later git command in that checkout or in the memory repo fails until someone deletes it, so context stops refreshing and `memory_propose` fails. | `src/context.ts` `ContextRepos.syncOnce`, `Memory.propose` | At startup, before any git runs, remove a leftover `index.lock` in each checkout and in the memory repo. |
| K18 | Unconfirmed: `read_inbox` (and `wait_for_message`) is at-most-once. Mail is marked read before the response reaches the agent, so a dropped HTTP response or a client crash loses those messages. | `src/core.ts` `takeInbox` | Read and acknowledge separately: return ids, mark read on an explicit `ack` or on the next call. |
| K19 | By P4 the ops agent is shared: its sessions, memory and answers mix what every principal's agents told it, so a mute never holds through it. Intended, and agents are told; listed so it isn't mistaken for a bug. | `src/ops-mcp.ts`, `src/ops.ts` | If mutes must ever hold through it: information-flow labels on every event, memory file and engine session (the option P4 turned down). |
| K20 | A system card Slack refuses for good (`invalid_blocks` …) is re-posted as plain text without its `switchboard` footer, so in that rare case it reads like ops text. The fallback says Slack refused the message, but ops text could imitate that line too. | `src/slack.ts` `deliver` | Re-post the fallback as a single section plus the footer, and fall back to bare text only if that is refused too. |
| K21 | If the process dies after Slack accepted a thread's first post (a page, a question card, a window card) but before its root was saved (`setSlackAnchor`), the sweep posts it again: a second top-level post, and replies under the first copy don't reach the thread. Any other post can be duplicated the same way (`slack_synced_seq` is saved after the post). | `src/slack.ts` `syncNow` | Record the intent before posting (a pending-root row) and, on restart, look the message up in the channel history before posting again. |
| K22 | Slack accepts a reply under a deleted parent and posts it top-level, with no error (checked live 2026-10-17). So the `thread_not_found`/`message_not_found` re-root fallback never fires for a deleted root: if a human deletes a thread's Slack root, every later reply in that thread becomes its own top-level post. | `src/slack.ts` | When deleting a root by hand, also clear that thread's `slack_channel`/`slack_ts` (migration 6 did this for agents-only threads). Detecting it needs `conversations.replies` before posting. |
| K23 | A standing card is posted on its own only when a queued change needs it. Pre-approval works through `node src/cli.ts admin ask-standing <principal>` (runbook §12), which posts that principal's card for the current version unless it was already posted or approved. There is no ops tool for it. | `src/windows.ts` `askStanding`, `src/cli.ts` | An ops tool, if the humans want to ask for their card in Slack. |
| K24 | `may_proceed` from the slot is per agent identity: every session sharing one identity (`alice/claude`) sees its queued changes, and one session's report closes the change for all of them. | `src/windows.ts` `resourceStatus` | One identity per session, if the humans want changes kept apart. |
| K25 | An item for a human (P3) the ops agent never tells or skips stays `pending`, listed in every later turn header of its thread (the newest 20). Nothing expires it, and nothing tells the agent it was never passed on. | `src/ops.ts` `render`, `human_items` | Expire pending items after a while and tell the agent, as unpresented asks are. |
| K26 | A human's reply to the ops agent in their DM (P3: where it tells them what their own agents wrote) reaches no agent unless the ops agent passes it on with `message_agents`. Replies under a #ops `tell_human` post reach the agents its items came from directly. | `src/ops-mcp.ts` `tell_human` | Put the items' agents in the DM's reach (a private thread per tell) if the humans want to answer agents directly. |
| K27 | A Claude Code session is woken by its `rewake` Stop hook (`asyncRewake`, checked live on 2.1.280; the 2.1.299 desktop build has the option), which reads Claude Code's session registry (`~/.claude/sessions/<pid>.json`), an internal, not a documented API. If a release changes either, sessions stop being woken and get their mail when they check (hooks, `inbox` counts on tool results, the idle ping). It re-arms at every turn's end, so a session idle for more than its 24 h timeout with no mail stops waiting until its next turn. A wake the client can't deliver (`codex queue` fails) still counts as told, so that mail waits for those too. | `clients/switchboard.mjs` | Check the client against each Claude Code upgrade; switch to a documented API if one appears. |
| K28 | The loop guard's 10-minute window is in memory: a restart forgets it, so an agent in a loop gets up to 12 more messages through after one. | `src/core.ts` `loopGuard` | Count from the inbox and events, with a sender session column, if restarts during loops matter. |
| K29 | A session that goes away without a word (Claude Code closed) is taken for closed only once its wake client has missed 10 minutes of polls: until the tick after that, mail already targeted at it waits for it (new mail goes to an online session). A session no client ever polled for (headless) keeps mail addressed to it until it is gone, 15 minutes unseen. Meanwhile a caller with no session still reads that mail. | `src/core.ts` `expireSessions` | Have the client say goodbye on exit (stdin closed), and move that session's mail at once. |
| K30 | A Codex thread is named, so kept online, while its client or its hook's waiter lives: until its Codex process exits. A Codex that runs many threads (an app-server) keeps a closed thread online, and a wake for it only parks the message (`codex queue` for a closed thread exits 0). | `clients/switchboard.mjs` | Ask Codex whether a thread is open, if it gains a way to say so, and stop naming closed ones. |
| K31 | Claude Code's messaging socket can't wake a Claude Desktop session: desktop builds (2.1.299) gate peer messages by the sender's permission class, which the host declares, not the frame, so a push from another process is held for the user's approval or dropped (seen live: written without error, never delivered). The client doesn't use the socket; `rewake` wakes Claude instead. Spoofing a class to get past the gate is out, and so are channels (launch flags or an allowlist). | `clients/switchboard.mjs` | Use a documented, user-approved channel if Claude Code adds one. |
